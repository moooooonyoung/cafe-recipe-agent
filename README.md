# 카페 레시피 가이드

## 1. 목적과 대상 사용자

카페 아르바이트생이 바쁜 매장에서 태블릿으로 음료 레시피를 빠르게 찾아보는 한국어 웹앱입니다. 제가 카페에서 일한 경험을 바탕으로, 읽기 쉽고 빨리 누를 수 있는 것을 기능 수보다 우선했습니다.

- **대상**: 가로 태블릿(터치)을 쓰는 매장 직원. 시연용으로 노트북 마우스 조작도 지원합니다.
- **핵심 기능**: 재고(있음/품절)에 따라 메뉴가 정상 / 대체 필요 / 제조 불가로 표시되고, 손님 옵션(온도·사이즈·샷 추가·당도)에 맞는 재료 양과 단계를 보여줍니다. 재료가 품절이면 대체 재료를 제안하고, 직원이 적용하거나 취소합니다.
- **LLM 없이 규칙 기반**입니다. 설계 첫 질문에서 LLM 대신 규칙 기반을 골랐습니다. 바쁜 매장에서 탭 한 번으로 빠르게 답이 나오고, 같은 입력이면 결과가 항상 같고, 마감 안에 끝낼 수 있기 때문입니다. 이 프로젝트의 에이전트 역할은 앱이 아니라 개발 도구인 Claude Code가 했습니다.

## 2. 실행·사용 방법

**배포 URL**: https://moooooonyoung.github.io/cafe-recipe-agent/

로컬 실행:

```
npm install
npm run dev     # http://localhost:5173/cafe-recipe-agent/
npm run check   # 타입 검사 + 테스트 + 빌드
```

사용 순서: 메뉴 카드 선택 → 옵션 확인 → 제조 가이드(단계를 탭하면 체크, 다시 탭하면 해제). 오른쪽 위 [재고 관리]에서 재료별 품절을 바꾸고, 초기화 버튼으로 기본값으로 되돌립니다. 재고는 브라우저 `localStorage`에 저장됩니다. 시연하려면 오트밀크나 얼음을 품절로 바꾼 뒤 메뉴 화면으로 돌아가 보세요.

## 3. 작업 과정 요약

`PLAN.md`의 10단계 중 9단계(배포·기능 동결)까지 순서대로 끝냈고, 10단계는 이 README와 시연 영상입니다. 요약하면 다음과 같습니다.

1. 설계: grill 스킬로 질문 12개에 답하며 `PLAN.md`를 만들었습니다. 코드는 그다음에 썼습니다.
2. 데이터와 규칙 로직: 레시피 초안을 Claude가 만들고, 제가 매장 기준으로 검토해 일부를 고쳤습니다. 대체 규칙은 제가 직접 검토해서 정했습니다(탄산수 → 물 삭제, 그래서 탄산수가 품절이면 에이드는 제조 불가. 바닐라 시럽 → 시럽 삭제, 시럽 → 바닐라 시럽 유지). 규칙 로직은 화면과 분리해 Vitest로 검증했습니다.
3. 화면: 재고 관리 → 메뉴 선택 → 옵션 확인 → 제조 가이드 순으로 만들고, 각 단계를 브라우저에서 직접 확인했습니다.
4. 화면 체크리스트: 태블릿 가로(1280×800)와 노트북 창에서 `PLAN.md` §4 항목을 모두 확인했습니다.
5. 배포: GitHub Pages. 계획(10/31)보다 이른 10/29에 끝냈고, 이후 기능을 동결했습니다.

## 4. Claude Code 증거와 검증 결과

**자동 검증**: `npm run check`가 통과합니다(테스트 147개). 테스트 이름은 "오트밀크 품절이면 우유를 제안한다"처럼 한국어 시나리오 문장입니다. 대표 사례(오트밀크 품절 → 우유 제안, 라지 + 샷 추가 → 4샷)와 엣지 케이스(탄산수 품절 → 에이드 제조 불가, 대체 후보가 모두 품절 → 제조 불가)를 포함하고, 레시피 데이터 검사(없는 재료 참조, 빠진 필드 등)도 테스트로 돌립니다.

**테스트가 실제로 잡아내는지 확인**: 대체 후보 순서(오트밀크 → 우유 → 두유)를 일부러 뒤집어 봤습니다. 테스트 74개 중 2개가 실패했고, 되돌린 뒤 `git diff`가 비어 있는 것과 전부 통과하는 것을 확인했습니다. 순서를 뒤집어도 통과한 테스트 2개는 "처음 순서"를 확인하지 않는다는 점도 알게 됐습니다.

## 5. 효과적이었던 방식 3가지

1. **코드 전에 설계 질문부터.** Claude가 질문을 하나씩 던지고 제가 답하며 설계를 정했습니다. 위 첫 스크린샷처럼 제안을 그대로 받지 않고 검토해서 결정했습니다.
2. **`CLAUDE.md`에 작업 규칙을 적기.** "단계가 끝나면 테스트 결과를 먼저 보여준 뒤 커밋", "파일은 셸 명령이 아니라 Write/Edit로 수정" 같은 규칙을 적었고, 실제로 지켜졌습니다.
3. **사람이 화면을 직접 보고 "이런 경우엔?"이라고 묻기.** Claude는 브라우저를 볼 수 없어서 화면 확인은 제가 맡았습니다. 테스트가 통과한 뒤에도 얼음이 품절인데 ICE 칩이 평소처럼 진한 파란색인 문제와, 오트밀크와 얼음이 함께 품절일 때 이유가 하나만 나오는 문제를 찾았습니다.

*화면을 보고 찾아 고친 문제. 안 되는 온도는 색뿐 아니라 흐림과 취소선으로도 알 수 있습니다.*

## 6. 어려웠던 점 3가지와 대응

1. **에이전트가 지시나 규칙을 놓침.** "하나씩 질문해 달라"고 했는데 6개를 한꺼번에 줬고, `CLAUDE.md`를 갱신하다 기존 규칙을 지웠습니다. → 다시 지시하자 바로잡았고, 지워진 규칙은 복원했습니다. 파일 수정은 Write/Edit로 하라는 규칙을 추가했습니다.
2. **의도하지 않은 파일이 push됨.** `git add -A`로 개인 설정 파일(`.claude/settings.local.json`)이 올라갔습니다. 비밀 정보는 없었지만 공개 저장소에 둘 파일이 아니었습니다. → `git rm --cached`로 추적을 끊고 `.gitignore`에 추가했습니다.
3. **세션이 끊겨 반쪽 작업이 남음.** 새 세션을 열자 커밋 안 된 변경이 18개 있었고, 파일 이름만 바꾸고 import를 고치지 않아 빌드와 테스트가 깨져 있었습니다. → "확인만 하고 고치지 마"라고 요청해 상태부터 파악한 뒤 이어갔고, 교훈으로 작은 단위로 자주 커밋하기로 했습니다.

![Claude가 CLAUDE.md 규칙을 실수로 지웠고 개인 설정 파일을 커밋에 포함시켰다고 스스로 보고한 터미널](docs/images/05-agent-mistakes.png)

*에이전트의 실수 두 가지를 Claude가 스스로 보고하고, 해결 방법을 제안한 장면.*

## 7. 알려진 한계

- **레시피의 대부분은 샘플 값입니다.** 제 근무 경험 기준으로 검토한 것은 아이스 아메리카노, 아이스 라떼, 핫 아메리카노뿐입니다. 그마저도 일부 값은 샘플이거나 추정입니다(아이스 라떼의 재료 양, 핫 아메리카노의 샷 수는 샘플 값, 라지 아이스 아메리카노의 얼음 200g은 추정). 나머지 메뉴, 메뉴 구성, 당도별 시럽 펌프 수, 기본 옵션은 실제 매장 검토 전의 샘플 값입니다. 대체 규칙은 제가 직접 검토해 정했습니다. 값마다 코드 주석에 출처가 있습니다. 실제 매장에서 쓰려면 검토가 필요합니다.
- 메뉴 카드의 '대체 필요' 이유는 옵션 **하나**(온도 또는 당도)만 바꿔서 만들 수 있을 때만 나옵니다. 두 옵션을 함께 바꿔야 하면 '제조 불가'로 표시됩니다.
- 새로고침하면 재고는 유지되지만, 보고 있던 화면(옵션·가이드)과 체크한 단계는 사라지고 메뉴 화면으로 돌아갑니다. 화면 상태를 저장하지 않기 때문입니다.
- 화면은 자동 테스트 없이 눈으로 확인했습니다. 버튼 크기는 CSS 최소값(56px 이상)을 코드로 점검하고 실제 사용으로 확인했을 뿐 실측하지는 않았습니다. 실제 태블릿 기기가 아니라 크롬 개발자 도구의 1280×800 화면에서 확인했습니다.
- 가로 태블릿만 지원합니다. LLM 자유 입력, 영어 UI, 다크 모드, 메뉴 검색 같은 선택 기능은 만들지 않았습니다.

## 8. 채점용 핵심 소스 파일

- `src/logic/status.ts`: 메뉴·옵션 상태(정상 / 대체 필요 / 제조 불가)와 카드 배지의 이유를 계산합니다.
- `src/logic/substitution.ts`: 품절 재료의 대체 후보를 제안하고, 적용·취소 결정을 처리합니다.
- `src/logic/recipe.ts`: 옵션에 따른 재료 목록과 양(레귤러/라지, 샷 추가, 당도)을 계산합니다.
- `src/data/data.test.ts`: 레시피·대체 규칙 데이터가 서로 올바르게 참조하는지 검사합니다.
- `src/screens/GuideScreen.tsx`: 옵션 요약, 재료 목록, 단계 체크, 대체 제안 배너를 그리는 제조 가이드 화면입니다.
